## 接入工具的老问题

在 MCP 之前，把外部能力接进 Agent 是一件重复劳动：每个 Agent 客户端有自己的插件格式，
每个数据源又要按客户端各写一遍适配层。

结果是 **N × M** 的工作量——N 个客户端，M 个工具，就要写 N × M 份代码，而且每边升级都要跟着改。

## MCP 的做法

MCP（Model Context Protocol）把这个矩阵拆成两半：工具侧实现一个 MCP server，
客户端侧支持 MCP 协议。之后任何支持 MCP 的客户端，都能直接使用任何 MCP server。

工作量从 N × M 降到 N + M。

它提供三类主要能力：

| 能力 | 作用 | 典型例子 |
| --- | --- | --- |
| Tools | 让模型主动调用动作 | 查数据库、调接口、执行命令 |
| Resources | 把数据暴露成可读上下文 | 文件、文档、日志 |
| Prompts | 预置的提示模板 | 固定流程的代码审查模板 |

## 什么时候值得自己写一个

不是所有场景都需要。我判断的标准是：**这套能力会不会被反复用到，并且需要多步操作**。

值得写的：

- 内部系统 API，且操作序列固定（查单号 → 取详情 → 生成摘要）
- 需要权限隔离的资源，不适合把凭证直接交给 Agent
- 多个客户端都要用同一套能力

不值得写的：一次性需求、只有一个客户端会用、用现成的命令行工具就能解决。

{: .warn }
工具数量不是越多越好。接几十个 MCP server 之后，模型在工具选择上会明显变慢、也更容易选错。按需接入比全量接入有效。

## 实践中的两个边界

**权限边界**：MCP server 是凭证的实际持有者，能力范围要按最小权限设计，
写操作和读操作最好分开授权。

**失败处理**：工具调用失败时，返回的错误信息质量直接决定 Agent 能否自救。
返回原始堆栈不如返回「参数不合法，expected int, got string」。

现成的 server 清单可以参考 [MCP 官方文档](https://modelcontextprotocol.io/)。
