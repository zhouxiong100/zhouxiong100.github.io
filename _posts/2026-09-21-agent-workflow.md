## 先给结论

一个任务适不适合交给 Agent，我会看两件事：

1. **验收标准是否明确**——如果我自己都说不出「做对了是什么样」，Agent 只会产出看起来对的代码
2. **上下文能否装下**——需要理解的文件、约定、历史决策，能不能一次性交代清楚

两条都满足，Agent 的效率通常是人工的几倍；只满足一条，往往要花更多时间返工。

## 位置一：读代码和定位问题

这是我用得最多、收益最稳定的场景。面对一个不熟悉的仓库，「这个报错是从哪里冒出来的」
这类问题，Agent 的检索和串联能力远强于自己翻文件。

提问时我尽量给三样东西：完整报错、复现步骤、我已经排除的可能。

{: .tip }
「我已经看过了 A 和 B，都不是」比「帮我看看为什么报错」有效得多——它省掉的是 Agent 最容易走弯路的部分。

## 位置二：写测试和样板代码

测试用例、类型定义、配置迁移脚本这类**结构固定、模式可复制**的工作，交给 Agent 几乎不需要返工。

关键是先给它一个仓库里已有的例子：*照着 `tests/test_user.py` 的风格，给 `order.py` 补测试*。
比抽象描述需求快得多，也更符合仓库现有风格。

## 位置三：批量机械改动

重命名、接口签名调整、依赖升级、日志格式统一——这类改动的判断逻辑简单，但涉及文件多。

这里的经验是**控制单次改动规模**：

- 一次只做一件事，不要在同一次对话里既重构又改功能
- 先让它列出计划，确认后再执行
- 每完成一部分就提交一次，出错时能干净回滚

{: .pitfall }
我最贵的一次踩坑，是让它一次性改了二十多个文件，中间某处改错了语义，而 diff 太大没人愿意逐行看，最后靠回滚重做。

## 位置四：多源信息整理

调研一个新库、对比几个方案时，Agent 能快速把散落的信息整理成结构化的表格。

但要注意：**它给出的结论需要抽样验证**。我通常让它只负责「列出维度 + 收集候选」，
结论部分自己判断。

## 我固定遵守的三条纪律

- 开始前让它复述一遍任务，确认理解一致再动手
- 大改动先要计划，不要直接给代码
- 每一步都要有可验证的结果，不要连续执行多个无验证步骤
