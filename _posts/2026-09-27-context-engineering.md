## 提示词的上限

很多人优化 Agent 效果时第一反应是改措辞。但措辞只影响它**如何理解**任务，
而任务能不能完成，取决于它**知道什么**。

同一个需求，配上仓库约定和两个已有例子，产出质量会有数量级的差别。

## 动作一：给约定，而不是给指令

把项目里的固定约定写成 Agent 每次都能读到的文件（常见命名如 `AGENTS.md`、`CLAUDE.md`），
而不是每轮对话重复交代。

这类文件值得写的内容：

- 项目结构与关键目录的职责
- 代码风格、测试和提交的约定
- 常见命令（怎么跑测试、怎么本地启动）
- 明确禁止的操作

{: .tip }
写约定时用「做什么」而不是「不要做什么」。约束越具体越容易被遵守，比如「新增依赖要先说明理由」比「谨慎引入依赖」有效。

## 动作二：把进度外置，不要留在对话里

长任务最大的敌人是上下文被中间过程占满。我的做法是把任务清单写进文件或 issue，
每完成一项就更新一次，对话只负责当前这一步。

这样做有两个好处：上下文始终干净；即使换个会话继续，也不会丢失进度。

## 动作三：及时清空，而不是硬撑

出现这些信号时，我通常会开新会话而不是继续追问：

- 它开始忘记前面已经确认过的决定
- 同样的错误反复出现，纠正后过几轮又犯了
- 对话里堆积了大量已经被推翻的方案

重新给一次干净的上下文，比在和污染的对话里挣扎要快得多。

{: .pitfall }
「再解释一遍」通常救不回一个已经混乱的会话。信息被推翻后仍然留在上下文里，会持续干扰后续判断。

## 一个简单的判断标准

每次给 Agent 补充信息前问自己：**这条信息是它现在完成任务必需的，还是我觉得有关的？**

只给必需的。上下文不是越多越好，无关信息会稀释真正重要的部分。
