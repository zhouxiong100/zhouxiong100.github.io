## 提示词的上限

很多人优化 Agent 效果时第一反应是改措辞。但措辞只影响它**如何理解**任务，
而任务能不能完成，取决于它**知道什么**。

同一个需求，配上仓库约定和两个已有例子，产出质量会有数量级的差别。

## 动作一：给约定，而不是给指令

把项目里的固定约定写成 Agent 每次都能读到的文件（常见命名如 `AGENTS.md`、`CLAUDE.md`），
而不是每轮对话重复交代。

这类文件值得写的内容：

- 项目结构与关键目录的职责
- 代码风格、测试和提交的约定
- 常见命令（怎么跑测试、怎么本地启动）
- 明确禁止的操作

{: .tip }
写约定时用「做什么」而不是「不要做什么」。约束越具体越容易被遵守，比如「新增依赖要先说明理由」比「谨慎引入依赖」有效。

一个最小可用的 `AGENTS.md` 模板大概长这样：

```markdown
# 项目约定

## 结构
- src/ 业务代码；src/lib 公共工具；tests/ 测试

## 命令
- 测试：npm test
- 本地启动：npm run dev

## 规则
- 改公共接口前先更新 README 中的示例
- 新增依赖前在 PR 里说明理由
- 提交信息用祈使句，描述「做了什么」
```

写完后的验证方法：开一个新会话，只说一句「按项目约定做 X」，看它会不会自己去读约定文件、用对命令。如果不会，说明约定写得不够具体，或者放的位置不对。

## 动作二：把进度外置，不要留在对话里

长任务最大的敌人是上下文被中间过程占满。我的做法是把任务清单写进文件或 issue，
每完成一项就更新一次，对话只负责当前这一步。

这样做有两个好处：上下文始终干净；即使换个会话继续，也不会丢失进度。

一个可以直接套用的任务清单格式：

```markdown
# 任务：给订单接口加限流

- [x] 1. 调研现有 middleware，选定接入点
- [ ] 2. 实现限流逻辑（当前步骤：先在 OrderService 里加计数）
- [ ] 3. 补集成测试：连续 10 次请求触发的行为
- [ ] 4. 更新接口文档

当前进度：步骤 2，已完成 Redis 计数器，待接入 middleware。
```

每完成一小步就让 Agent 更新一次这个文件。开新会话时，把文件发给它 + 一句「从当前进度继续」，几秒钟就能接上，不用复述半小时的来龙去脉。

## 动作三：及时清空，而不是硬撑

出现这些信号时，我通常会开新会话而不是继续追问：

- 它开始忘记前面已经确认过的决定
- 同样的错误反复出现，纠正后过几轮又犯了
- 对话里堆积了大量已经被推翻的方案

重新给一次干净的上下文，比在和污染的对话里挣扎要快得多。

{: .pitfall }
「再解释一遍」通常救不回一个已经混乱的会话。信息被推翻后仍然留在上下文里，会持续干扰后续判断。

清空不等于从头再来，正确姿势是**带一份压缩过的上下文开新会话**：

1. 写两句任务目标（这次到底要什么）
2. 列出已经确认过的关键决定（每条一行，不要过程）
3. 附上当前有效的代码状态，而不是被推翻的旧版本
4. 明确说「忽略之前的所有中间讨论」

这样新会话拿到的是「结论 + 现状」，而不是「全过程 + 一堆已经被否掉的方案」。

## 一个简单的判断标准

每次给 Agent 补充信息前问自己：**这条信息是它现在完成任务必需的，还是我觉得有关的？**

只给必需的。上下文不是越多越好，无关信息会稀释真正重要的部分。

## 一页速查

| 场景 | 该怎么做 |
| ---- | -------- |
| 每轮都要重复交代规则 | 写进 `AGENTS.md`，让 Agent 自己读 |
| 长任务做到一半上下文满了 | 把任务清单外置成文件，逐条更新 |
| 它开始重复犯错、忘记决定 | 开新会话，带「结论+现状」重启 |
| 想补充背景资料 | 只给完成任务必需的那一条 |

上下文管理的本质就一句话：**让 Agent 的上下文里始终只有「现在把活干完」所需要的东西。**
