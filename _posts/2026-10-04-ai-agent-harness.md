## 先给结论

**Chatbot 主要负责回应，Workflow 按预先写好的步骤执行，Agent 则会根据当前情况选择下一步行动。**

但 Agent 并不是一个突然变聪明的独立模型。它通常由一个负责理解与判断的 LLM，加上一套负责工具、流程、上下文和安全约束的运行机制组成。工程里常把这套运行机制称为 **Harness**。

可以先用这个近似公式理解：

> **LLM + Harness ≈ AI Agent**

这里的“≈”很重要：Agent 没有唯一标准定义，Harness 也不是某个固定产品或单一组件。这个公式是帮助理解系统分工的模型，不是严格的数学等式。

## Chatbot、Workflow 和 Agent 有什么不同？

假设目标都是“帮我找出这次发布失败的原因”。三种系统的差异，不在于界面是不是聊天框，而在于**谁决定下一步做什么**。

![Chatbot、Workflow 与 Agent 的决策方式对比：回答一次、执行固定步骤、根据结果循环决策]({{ '/assets/images/agent-chatbot-workflow.svg' | relative_url }})

| 类型 | 谁决定下一步 | 典型过程 | 适合的任务 |
| --- | --- | --- | --- |
| Chatbot | 用户逐轮提问 | 用户提问 → 模型回答 | 问答、解释、头脑风暴 |
| Workflow | 开发者预先定义 | 步骤 A → 步骤 B → 步骤 C | 稳定、可预测、规则明确的流程 |
| Agent | 模型根据观察结果选择，受系统规则约束 | 观察 → 选择行动 → 检查结果 → 再决定 | 需要探索、会遇到不同分支的任务 |

### Chatbot：一问一答为主

典型 Chatbot 接收消息、生成回复，然后等待用户下一轮指令。它可以很有帮助，也可以调用工具；**只要它主要是在等人告诉它下一步做什么，它就仍然更像对话助手。**

所以“能聊天”并不是 Agent 的判断标准。反过来，一个 Agent 也可以通过聊天界面使用。

### Workflow：步骤由人提前编排

Workflow 把过程写成固定流程。例如：

1. 读取部署日志
2. 搜索错误码
3. 生成故障摘要
4. 发送通知

每一步都可以使用 LLM，但流程的分支和顺序主要由开发者预先决定。它的优势是**可预测、容易测试和审计**；如果需要临时改变调查方向，通常要在流程中事先写好相应分支。

### Agent：步骤会随观察结果调整

Agent 面对同一个故障目标，可能先读日志；如果发现是权限错误，就检查权限配置；如果发现是测试失败，就查看相关改动并运行测试。它不只生成文本，还会在允许的范围内调用工具、读取结果，再决定是否继续。

这不意味着 Agent 完全自由，也不意味着模型每次都能做出正确选择。Agent 的可行动作、循环次数、预算和审批要求，都应该由 Harness 限定。

{: .tip }
一个实用的区分问题：**下一步是代码事先规定的，还是系统根据刚得到的结果动态选择的？** 前者更像 Workflow；后者更有 Agent 的特征。现实系统往往是两者混合。

## Harness 是什么？

**Harness 是围绕 LLM 搭建的运行环境与控制层**：它把用户目标交给模型，把模型的行动接到真实工具上，再把观察结果送回来，同时管理上下文、权限和停止条件。

可以把 LLM 想成负责判断的引擎，把 Harness 想成让引擎安全完成任务的整台机器：方向盘、仪表、刹车、路线和维修记录都不在引擎本身里。

![AI Agent 的 Harness 结构：围绕 LLM 管理输入输出、工具、状态、循环、安全与验证]({{ '/assets/images/agent-harness.svg' | relative_url }})

不同框架对 Harness 的边界划分会有差异，但常见职责包括：

- **指令与输入**：整理系统规则、用户目标，以及当前任务所需的信息。
- **工具接口**：把文件、搜索、终端、浏览器或 API 等能力提供给模型，并处理工具调用。
- **控制循环**：决定何时把结果交回模型、何时继续执行，以及何时停止。
- **上下文与状态**：保存当前进度和必要的历史，避免任务只依赖不断增长的对话记录。
- **安全与权限**：限制可访问的资源和可执行的操作；必要时要求人工确认。
- **验证与恢复**：运行测试或检查结果，处理超时、失败和重试，并留下可观察的记录。

Harness 不一定是一个单独的软件包。简单场景里，它可能只是一个工具调用循环和几条约束；在编程 Agent 中，则可能包含代码仓库访问、终端、差异检查、测试和权限确认。

## 一次 Agent 任务是怎么跑起来的？

以“定位并修复一个测试失败”为例：

1. **Harness 准备上下文**：提供用户目标、项目约定和测试失败信息。
2. **LLM 判断下一步**：认为需要先查看相关代码，于是请求读取文件。
3. **Harness 检查并执行**：确认读取操作在许可范围内，调用文件工具。
4. **结果返回给 LLM**：模型根据代码和错误信息决定运行相关测试。
5. **Harness 执行并验证**：运行测试，把输出交回模型。
6. **结束或继续**：测试通过且改动符合要求，就汇报结果；否则继续调查，或在达到限制时停止并说明原因。

这个循环里，LLM 负责提出判断和行动，Harness 负责把行动转成受控的真实操作。**没有工具执行和结果回传，Agent 只能说它准备怎么做；没有权限和停止机制，它又可能做得过多。**

## 为什么 Harness 和模型同样重要？

给同一个 LLM 接上不同的 Harness，Agent 的实际能力会明显不同：

- 没有文件读取能力，它无法真正检查代码仓库。
- 没有工具结果回传，它无法依据执行结果修正判断。
- 没有状态管理，长任务容易遗失进度或重复工作。
- 没有权限边界，误判可能变成不可逆的操作。
- 没有验证步骤，它可能把“看起来完成”误报成“确实完成”。

因此，评估 Agent 时不应只比较模型回答得多聪明，也要看它**能观察什么、能做什么、如何检查结果、出了错怎么停下来**。

## 什么时候用 Agent，什么时候不用？

如果步骤明确且很少变化，优先用普通代码或 Workflow：行为更稳定，成本也更容易控制。只有当任务确实需要根据中间结果调整路径时，Agent 的自主决策才有价值。

开始设计一个 Agent 前，可以先回答四个问题：

1. **目标是什么？** 能不能判断任务是否完成？
2. **它需要哪些动作？** 是否每个工具都确实必要？
3. **它能在哪里犯错？** 哪些操作必须限制或要求确认？
4. **如何证明结果正确？** 有测试、校验规则或人工验收吗？

一个好的 Agent，不是“尽可能自主”，而是**只在需要判断的地方自主，在需要确定性的地方交给明确规则**。

## 一句话回顾

- **Chatbot**：主要和你对话。
- **Workflow**：按照人预先编排的步骤执行。
- **Agent**：依据目标和观察结果，在约束内选择下一步。
- **Harness**：负责上下文、工具、控制循环、安全和验证的运行机制。

所以，“LLM + Harness ≈ AI Agent”最有用的地方，是提醒我们：**模型提供判断能力，系统工程决定这种能力能否可靠地落到现实任务里。**
